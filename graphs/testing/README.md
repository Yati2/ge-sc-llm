# Graph Testing README

This folder contains test-time graph artifacts and prediction exports for running MANDO-HGT style inference in this workspace.

## 1) What The Model Expects

The graph classifier builds its architecture from the input `.gpickle` graph schema:

- Node types
- Edge/relation types
- Node attributes used by the model pipeline

Because of that, **checkpoint loading only works when the checkpoint was trained with the same graph schema**.

In practice, schema mismatch appears as:

- unexpected keys
- missing keys
- tensor shape mismatch

This is why a checkpoint can fail to load even when file paths are correct.

## 2) Checkpoint Meaning

A checkpoint (`.pth`) is trained model weights.

- Without checkpoint: the model runs with random/partially initialized weights, so predictions are not reliable.
- With checkpoint: predictions are meaningful only if checkpoint schema matches graph schema.

In this project, checkpoints are typically **binary detectors per vulnerability type**:

- class `0`: not vulnerable for that type
- class `1`: vulnerable for that type

## 3) Two Checkpoint Variants In This Repo

Checkpoint names under `checkpoints/graph_detection/nodetype` follow two patterns:

1. `*_hgt.pth`
2. `*_tree_sitter_cfg_cg_hgt.pth`

Interpretation:

- `*_hgt.pth`: baseline/non-tree-sitter variant lineage
- `*_tree_sitter_cfg_cg_hgt.pth`: tree-sitter CFG+CG variant lineage

Both are type-specific detectors, but they come from different training pipelines/checkpoint families.

## 4) Graph Types You Currently Have

### A) CFG-only test graphs

Generated by `generate_cfg_graphs.py` and stored at:

- `graphs/testing/tier_1_complete_cfg_tree_sitter/*.gpickle`

These are useful for stress-testing and heuristic runs, but they are not guaranteed to match trained checkpoint schema.

### B) Repo-provided graph_detection graphs (model-compatible pairs)

Stored at:

- `graphs/graph_detection/*_cfg_cg_compressed_graphs.gpickle`
- `graphs/graph_detection/*_tree_sitter_cfg_cg_compressed_graphs.gpickle`

These are the graph families intended to pair with graph-detection checkpoints.

## 5) Compatibility Summary

### Real inference (recommended)

Use a **matching pair**:

- graph from `graphs/graph_detection/...`
- checkpoint from `checkpoints/graph_detection/nodetype/...`

### CFG-only batch run (what was done here)

`run_cfg_only_all_checkpoints.py` uses partial state loading to avoid hard crashes and still produce outputs. This is useful for analysis, but not equivalent to fully schema-matched inference.

## 6) Outputs In This Folder

### Raw all-checkpoint run

- `cfg_only_all_checkpoint_predictions.csv`
- `cfg_only_all_checkpoint_summary.txt`

### Per-checkpoint exports

- `by_checkpoint/*_positives.csv`
- `by_checkpoint/*_errors.csv`
- `by_checkpoint/checkpoint_export_summary.csv`

These files let you inspect:

- which contracts were predicted vulnerable per checkpoint
- probabilities (`prob_class_1`)
- which contracts failed and why

## 7) Practical Interpretation Rules

For each checkpoint row:

1. Check `status` first.
2. If `status=ok`:
   - `predicted_label=1` means vulnerable for that checkpoint's category.
   - `prob_class_1` is confidence-like score for class 1.
3. If `status=error`, use the corresponding `*_errors.csv` to inspect reason.

---

If you later restore a full CFG+CG generator in `process_graphs`, regenerate graphs in the same schema family as the target checkpoint before running production inference.
